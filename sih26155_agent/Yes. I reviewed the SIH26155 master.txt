# SIH26155 — Final End-to-End Architecture

## 1. What are we solving?

### The real problem

NTRO can have a very large network containing devices from different vendors:

* Cisco
* Juniper
* Fortinet
* Palo Alto
* Arista
* SONiC
* Cloud-native firewalls
* and potentially new/unknown platforms

Each vendor can represent the same security setting differently.

For example, conceptually:

```text
Cisco
"no ip http server"

Juniper
"different syntax"

Fortinet
"different syntax again"
```

But the security question is the same:

> **Is HTTP-based management enabled?**

At the same time, security frameworks such as CIS, NIST, DISA STIG and ISO define security requirements, but they don't provide one universal configuration language for all these vendors. 

### The biggest technical problem

Traditional systems generally depend heavily on predefined vendor parsers.

If a new syntax appears:

```text
Unknown command
      ↓
Parser doesn't understand
      ↓
What should the system do?
```

A dangerous AI system might **guess**.

Your system takes a safer approach:

> **If it doesn't have enough evidence, it doesn't guess.**

The master specification explicitly defines this as the core problem being solved. 

---

# 2. Our solution in one sentence

> **An autonomous security compliance agent that accepts a high-level audit goal, discovers and understands multi-vendor network configurations, converts them into a common security representation, safely handles previously unseen syntax through retrieval and human confirmation, evaluates them using deterministic security rules, supports organization-specific policies, and maintains blockchain-backed integrity of important rules, approvals and reports.**

# 11. Universal Security Baseline

This is the **bridge between vendors and security rules**.

Everything gets converted into a common representation.

For example:

```text

Juniper

       ↓
       ↓
       ↓
Universal Security Baseline
```

Example:

```json

      "protocol_version": 2
```

Now your compliance engine doesn't need to know how Cisco or Juniper wrote the original command.


This normalization architecture is explicitly central to the current design.

# 12. Pydantic

Pydantic is the **security data validator**.

It ensures:

```text
Field exists
Value has correct type
Structure is valid
```

For example:

```text
management.telnet.enabled
```

expects:

```text
Boolean
```

Therefore:

```text
true       ✓
false      ✓
"hello"    ✗
123        ✗
```

This prevents bad AI/retrieval output from silently entering your security system.

# 17. Blockchain Layer

This is where your **Blockchain & Cybersecurity theme** becomes meaningful.

Blockchain is **not the brain** of the system.

It is the **trust layer**.

We use it for:

### Rule integrity

```text

     ↓
Hash
     ↓
Blockchain
```

If someone modifies the rule later:

```text
Modified Rule
     ↓
New Hash
     ↓
Doesn't match blockchain
     ↓
TAMPERING DETECTED
```

---

### Knowledge approval

```text
New mapping
     ↓
Reviewer A
     ↓
Reviewer B
     ↓
Approval proof
     ↓
Blockchain
```

---

### Report integrity

```text
Final PDF
   ↓
SHA-256 hash
   ↓
Blockchain
```

If somebody changes:

```text
FAIL → PASS
```

the hash changes.

Therefore:

```text
Blockchain hash ≠ Report hash

→ REPORT TAMPERED
```

Your uploaded blockchain design explicitly defines this role.
