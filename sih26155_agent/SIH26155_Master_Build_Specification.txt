The rule that must never be violated by any future change: the AI/LLM
layer NEVER produces a compliance verdict. It only ever produces evidence,
candidates, and confidence scores. A separate, deterministic rule engine
(rule_engine.py) is the ONLY thing that outputs PASS/FAIL. Every backend
endpoint and every frontend component in this project respects that
boundary. Do not add a code path that lets an LLM call set a FindingStatus
directly.

1. The Problem, and Why the Architecture Looks Like This

PS ID: SIH26155 — AI-Driven Multi-Vendor Network Security Compliance
Auditor. Organization: NTRO. Theme: Blockchain & Cybersecurity.

Enterprise networks run devices from many vendors (Cisco, Juniper,
Fortinet, Palo Alto, Arista, SONiC, cloud-native firewalls), each with its
own configuration syntax. Security frameworks (CIS Benchmarks, NIST
SP 800-53, DISA STIGs, ISO/IEC 27001) define what "secure" looks like in
plain language, not in any vendor's dialect. Existing tools either use
rigid hand-coded parsers (break on any unseen syntax) or let an AI decide
compliance directly (unauditable, unpredictable).

The problem we actually solve: how does a compliance system behave
correctly when it meets configuration syntax it has never seen before —
without silently guessing, without a code rewrite, and without ever letting
an AI layer decide the security verdict.

The architecture, one paragraph: every vendor's config is normalized
into one common structure (the Universal Security Baseline). A
deterministic parser (Layer 1) handles known syntax at full confidence.
Anything unrecognized is flagged, not guessed at. A retrieval-based
candidate-suggestion layer (Layer 2) proposes — never asserts — an
interpretation for unknown syntax, with a confidence score computed from
checkable signals (retrieval similarity, parser certainty, schema
validation, vendor-fingerprint confidence), never from an LLM's own
self-report. A human confirms or rejects any low-confidence mapping through
a schema-validated UI. Once confirmed, the mapping is persisted and reused
automatically — including across every other device sharing the same
previously-unseen pattern (the "reflection"/clustering behavior). A wholly
separate, deterministic rule engine evaluates 20 CIS-derived rules against
the normalized baseline and is the only component that ever outputs
PASS/FAIL/NEEDS_HUMAN_REVIEW/NOT_APPLICABLE. An orchestration layer (the
"agent") sits above all of this, accepting a goal ("audit everything and
report critical findings") and sequencing the pipeline itself, rather than
requiring a person to click through every stage.

2.2 Why the agent's internal imports are "flat"

Files inside agent/ (e.g. agent/agent.py) import siblings directly —
from planner import plan_from_goal, not from agent.planner import plan_from_goal. This was a deliberate original design so agent/ could be
run standalone (cd agent && python3 demo_mission.py) without needing to
be installed as a package. This has one consequence you must respect:
main.py adds BOTH backend/ and backend/agent/ to sys.path, and
imports the orchestrator as a flat module (import agent as agent_module),
NOT as a dotted subpackage (from agent.agent import ...) — the dotted
form breaks because agent.py (a file) and agent/ (a package with the
same name) collide once both directories are on the path. If you refactor
this, either:

Keep the flat-import convention and keep both path inserts in the same order (backend/ first, backend/agent/ second — order matters, see main.py comments), OR

Properly convert agent/'s internals to relative imports (from .planner import ...) and treat it as a real installable package — larger refactor, not done in this pass.

2.3 What's genuinely new in this integration pass

agent.py: added an optional on_log callback to run_mission() so the API layer can capture the trace as a list instead of only printing it. Also added a before/after snapshot: compliance is now evaluated once right after parsing (before any training corrections apply) and again at the end, producing a flips list — every (device, rule_id, before_status, after_status) tuple that changed. This generalizes the CLI demo's single hardcoded example (CIS-AUTH-03 on dev03) to whatever the fixture set actually produces, which is what the frontend's "Before → After" section renders.

state.py: added flips: List[Dict] to MissionState.

main.py: entirely new — the FastAPI app (see Section 4 for the full endpoint contract).

2.4 Deliberate design choice: no WebSocket streaming (yet)

/api/mission/run runs the mission synchronously and returns the
entire captured trace as an array of strings in one JSON response. The
frontend replays this array with a ~140ms delay between lines
(MissionTraceLog.jsx) to produce the live-feeling Mission Mode console.

This was a deliberate simplicity/reliability tradeoff for this build pass,
not an oversight — see Section 6.1 for the exact WebSocket upgrade path if
true server-push is wanted later.

6. What's NOT Done — Exact Upgrade Paths

6.1 Real-time WebSocket streaming (currently: replay of a captured array)

Replace POST /api/mission/run's synchronous execution with a WebSocket
endpoint. agent.run_mission() already accepts on_log, so the change is
localized:

@app.websocket("/ws/mission")
async def mission_ws(ws: WebSocket):
    await ws.accept()
    goal = (await ws.receive_json())["goal"]
    loop = asyncio.get_event_loop()
    def on_log(msg):
        asyncio.run_coroutine_threadsafe(ws.send_json({"type": "log", "message": msg}), loop)
    mission = await loop.run_in_executor(
        None, lambda: agent.run_mission(goal, DEVICE_CONFIGS, trace=False, on_log=on_log)
    )
    await ws.send_json({"type": "done", "result": {...}})


Frontend change: replace MissionTraceLog's setTimeout replay loop with
a WebSocket onmessage handler appending to the same lines state array
— the animation code (motion.div per line) does not need to change at all.

6.2 True interactive human-in-the-loop for Mission Mode

Right now, /api/mission/run's grouped-review confirmation is
auto-approved by SecurityAuditAgent._auto_approve() — the mission
runs start-to-finish without actually pausing for a human click. The
standalone TrainingWizard (Section 4) IS fully interactive and real.
To make Mission Mode itself pause for a real human:

Extend the WebSocket protocol above with a review_request / review_response message pair.

Replace human_approval_callback in SecurityAuditAgent.__init__ with one that blocks on a threading.Event set when the WebSocket receives the frontend's response.

Frontend: when a review_request message arrives, render the same GroupedReviewCard but with live Confirm/Reject buttons instead of a static status, and send the response back over the same socket.

6.3 Real file uploads instead of fixtures

agent/fixtures.py's DEVICE_CONFIGS dict is hardcoded. Add:
POST /api/mission/upload accepting multipart file uploads, saving to a
temp dir, and passing that directory to discover_configs() (already
supports a real directory path — see agent/tools/discovery.py). Add a
file-picker UI element to MissionControl.jsx.

6.4 Multi-user / multi-session state

main.py currently uses module-level global state (_kb,
_training_kb, _last_detection) — fine for a single-demo-session backend,
not safe for concurrent users. Before any real deployment: move this
state into a session object keyed by a session ID (cookie or JWT), or a
proper datastore (Redis/Postgres) for the knowledge base and episodic
memory.

6.5 Vendor coverage

Only Cisco IOS and Juniper Junos have real parsers (agent/tools/parsing.py).
FortiOS (and everything else) correctly degrades to "needs review" rather
than guessing — this is intentional graceful degradation, not a bug — but
adding real parser rule-sets for more vendors is the highest-value next
increment for demo breadth. Follow the existing _rule(pattern, handler)
pattern in parsing.py.

6.6 The planner is not yet an LLM

agent/planner.py's plan_from_goal() is deterministic keyword matching,
clearly marked as the LLM swap-in point. Replacing it with a real LLM call
is optional — the current MVP's plan is nearly fixed regardless of goal
phrasing, so this is a "nice to have," not a blocker.

7. Research Paper Key Points (condensed, for grounding design decisions)

Batfish (ACM SIGCOMM 2023) — Industrial, decade-proven network config
analysis tool. Validates the core idea of normalizing heterogeneous vendor
configs into one internal representation before analysis (their Stage 1).
Their explicit lesson: hand-coded per-vendor parsers (ANTLR grammars) are
the standard approach, and adding a new vendor means writing new grammar —
exactly the limitation our training loop is designed to soften without
replacing deterministic parsing for known vendors.

Confucius (ACM SIGCOMM 2025, Meta) — Production multi-agent LLM
framework for network management, 2 years live, 60+ applications. Their
explicit design principles: "Separate Reasoning from Factual Knowledge"
and "Not Depend on Fine-tuning" — independently arriving at the same
philosophy as this project (LLM for orchestration/interpretation only,
deterministic tools for facts and decisions). Their named failure modes —
hallucination, "failure to fail early," context lost over long sessions —
are honest, published evidence for why this project keeps the compliance
verdict outside any LLM's reach entirely, not just discouraged.

Symmetry/MDPI (2026) — LLM-driven IoT/network security analysis via
YANG/NETCONF + Model-Driven Engineering + OCL rules. Narrower scope than
this project (structured YANG models, not raw heterogeneous CLI text), but
provides quantified evidence that LLM accuracy measurably degrades as
candidate/command-set size grows for both commercial and local models —
external support for gating low-confidence AI output behind human
confirmation rather than trusting it outright.

TopoIntent (arXiv 2026) — Closest published architecture to this
project's schema-contract + staged-pipeline + additive-repair pattern.
Important distinction, not just similarity: TopoIntent's compliance
checker itself is an LLM (classifying safeguards as
satisfied/unsatisfied/manual-review) — determinism there lives in schema
validation and post-processing, not in the verdict. This project's rule
engine is stricter: the verdict is produced by code with zero LLM
involvement at that step. Also, TopoIntent generates new topologies from
intent; this project audits already-deployed real configs in
heterogeneous existing syntax — a different problem, not a strictly harder
or easier one.

The one line to have ready if a judge has read these: "Batfish and
TopoIntent validate that our normalization and schema-contract approach is
industry-aligned. Confucius validates our agent-over-deterministic-tools
philosophy at production scale. None of them enforce as strict a boundary
between AI interpretation and the compliance verdict as this project does
— that separation is our specific contribution."
